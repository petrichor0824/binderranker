# v0.3 Architecture Direction

## 1. Product identity

The project is centered on BinderRanker.

BinderRanker provides interpretable scoring, ranking, layered screening,
and prioritization of generated protein backbone candidates.

The Agent is an optional interaction layer. It is not the scientific core.

The v0.3 primary workflow is:

generated backbone PDBs
→ validation
→ BinderRanker
→ ranking / layered screening / explanation
→ downstream prioritization

The project does not attempt to replace RFdiffusion, ProteinMPNN,
structure prediction, simulation, or experimental validation.

## 2. Architectural rule

Scientific facts, workflow state, safety decisions, approval,
execution, provenance, and BinderRanker results are owned by
deterministic Python code.

Models may understand natural language and explain validated evidence.
Models must not:

- change BinderRanker scores;
- fabricate scientific evidence;
- approve their own actions;
- bypass execution guards;
- decide that protected task evidence may be deleted;
- generate arbitrary commands for execution.

## 3. Target architecture

User
→ Built-in Chat / OpenClaw
→ constrained Tool API
→ deterministic PDA Core
→ BinderRanker

Built-in Chat should migrate toward Pydantic AI.

OpenClaw should be an optional external integration rather than
the core runtime.

## 4. Module decisions

### KEEP

- planner.py deterministic planning rules
- task_lifecycle.py
- task_recovery.py
- workspace task/path safety
- approval and execution guards
- provenance and run-status logic
- BinderRanker result parsing
- deterministic result presentation

### KEEP / EXTRACT

- PlanningSession data model
- natural-language preparation persistence
- incomplete-session persistence
- plan/result evidence readers
- ranking preview and pool/provenance formatting
- strict model-output validation rules

### REPLACE BY PYDANTIC AI

- LocalAgentOrchestrator
- handwritten natural-language intent classification
- general dialogue routing
- provider-specific Agent abstractions
- model task-selection logic
- model HTTP/provider glue

### DEPRECATE AFTER PARITY

- chat_dialogue.py as a monolithic Agent runtime
- process_chat_message() as a monolithic Chat controller
- legacy RequestParserProvider / StructuredJSONProvider abstractions
- legacy OpenAI-compatible provider implementation

These components remain temporarily for compatibility and regression
testing until the replacement path reaches behavioral parity.

## 5. Migration rule

Do not rewrite the deterministic Core.

Migration order:

1. Stabilize remaining v0.3 P0 Core issues.
2. Expose a small stable Tool API.
3. Run a Pydantic AI spike against existing behavioral tests.
4. Migrate built-in Chat incrementally.
5. Deprecate the old handwritten Agent runtime only after parity.
6. Add an optional OpenClaw/MCP adapter.

Existing Chat tests should be treated as behavioral regression and
evaluation cases rather than discarded with the old implementation.

## 6. Development gate

Before adding new Agent behavior, ask:

Does this improve BinderRanker backbone screening,
workflow reliability, evidence handling, or usability?

If the feature mainly expands a general-purpose Agent runtime,
do not add it to the legacy Chat implementation.

## 7. Framework-first engineering rule

The Agent is a product interaction layer, not the scientific innovation
of Protein Design Agent.

For generic Agent infrastructure, prefer mature frameworks before
building custom runtime code.

Examples include:

- natural-language understanding;
- tool selection and tool-calling loops;
- conversation/session handling;
- model/provider portability;
- structured tool invocation;
- human-in-the-loop pause/resume;
- Agent testing infrastructure.

Custom implementation is justified when it materially improves
PDA-specific scientific, workflow, evidence, safety, or BinderRanker
behavior.

The target default is:

Pydantic AI
→ constrained PDA Tool API
→ deterministic PDA application/core services
→ BinderRanker.

Do not build a second general-purpose Agent framework inside PDA.


## 8. Root-cause-first engineering rule

Bug fixes should target the violated architectural boundary, invariant,
or abstraction whenever practical.

Do not accumulate phrase-specific, provider-specific, or
task-state-specific patches merely to satisfy individual examples.

If fixing a behavior requires repeated special cases, keyword lists,
or additional branches in a legacy router, stop and reevaluate the
underlying abstraction first.

Tests should primarily protect behavioral invariants and Tool
contracts. Concrete user phrases are acceptance examples, not the
implementation model.


## 9. Legacy Agent runtime freeze

The handwritten Agent runtime is feature-frozen.

In particular, do not add new general Agent behavior to:

- `chat_dialogue.py`;
- `LocalAgentOrchestrator`;
- handwritten dialogue intent routing;
- legacy provider-driven Agent control flow.

Only critical compatibility, data-integrity, or security fixes are
allowed while the replacement path is being built.

New Agent behavior should be implemented through the new Tool API and
Pydantic AI path.


## 10. Migration invariant

The migration must preserve domain behavior without preserving legacy
implementation details.

KEEP:

- BinderRanker scientific logic;
- deterministic planning;
- PlanningSession semantics;
- task lifecycle and recovery;
- approval, frozen hashes, and execution guards;
- provenance and result evidence;
- scientific capability boundaries;
- deterministic validation and public error boundaries.

EXTRACT:

- preparation and resume services;
- dataset services;
- status and plan readers;
- result-analysis services;
- deterministic task navigation.

REPLACE / RETIRE AFTER PARITY:

- handwritten intent classification;
- monolithic Chat routing;
- LocalAgentOrchestrator;
- provider capability-driven business routing;
- semantic fallback patches;
- legacy Agent loop infrastructure.

Existing tests protect required behavior and safety invariants, not the
continued existence of the old runtime.
