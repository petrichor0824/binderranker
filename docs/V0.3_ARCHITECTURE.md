# v0.3 Architecture Direction

## 1. Product identity

The project is centered on BinderRanker.

BinderRanker is an interpretable ranking and layered screening system for
generated protein backbone candidates. It provides deterministic scoring,
ranking, screening, and prioritization for downstream validation.

BinderRanker is not an Agent product. Agent interfaces are optional interaction
layers. They are not the scientific core.

The v0.3 primary workflow is:

generated backbone PDBs
→ validation
→ BinderRanker
→ ranking / layered screening / explanation
→ downstream prioritization

The project does not attempt to replace RFdiffusion, ProteinMPNN,
structure prediction, simulation, or experimental validation.

## 2. Architectural rule

Scientific facts, workflow state, safety decisions, approval,
execution, provenance, and BinderRanker results are owned by
deterministic Python code.

Models may understand natural language and explain validated evidence.
Models must not:

- change BinderRanker scores;
- fabricate scientific evidence;
- approve their own actions;
- bypass execution guards;
- decide that protected task evidence may be deleted;
- generate arbitrary commands for execution.

## 3. Target architecture

Direct CLI / Python ─────────┐
Built-in Agent (optional) ───┼→ BinderRanker Tool API
External Agents (optional) ──┘→ deterministic BinderRanker Core
                               → BinderRanker Engine

The scientific capability is identical across access paths. External Agents
call BinderRanker through the stable Tool/API boundary; they do not become the
product and must not duplicate ranking or screening logic.

The existing built-in Agent may remain as a supported reference interaction
layer. A framework migration, including Pydantic AI, is not an architectural
objective by itself and requires a separate scoped maintenance case.

## 4. Module decisions

### KEEP

- planner.py deterministic planning rules
- task_lifecycle.py
- task_recovery.py
- workspace task/path safety
- approval and execution guards
- provenance and run-status logic
- BinderRanker result parsing
- deterministic result presentation

### KEEP / EXTRACT

- PlanningSession data model
- natural-language preparation persistence
- incomplete-session persistence
- plan/result evidence readers
- ranking preview and pool/provenance formatting
- strict model-output validation rules

### OPTIONAL INTERACTION-LAYER REASSESSMENT

- LocalAgentOrchestrator
- handwritten natural-language intent classification
- general dialogue routing
- provider-specific Agent abstractions
- model task-selection logic
- model HTTP/provider glue
- external Agent adapters on the stable Tool API

These components are reassessed only when doing so directly improves
BinderRanker usability or reduces maintenance burden. No framework migration
is pre-approved by this document.

### RETAIN FOR COMPATIBILITY UNLESS A SEPARATE REVIEW APPROVES CHANGE

- chat_dialogue.py as a monolithic Agent runtime
- process_chat_message() as a monolithic Chat controller
- legacy RequestParserProvider / StructuredJSONProvider abstractions
- legacy OpenAI-compatible provider implementation

These components remain for compatibility and regression testing. If a future
scoped replacement is approved, behavioral and safety parity is required
before deprecation.

## 5. Development order

Do not rewrite the deterministic Core.

Priority order:

1. Scientific ranking and screening capability.
2. Reproducibility and validation.
3. Stable BinderRanker Tool/API interfaces.
4. External Agent ecosystem compatibility.

Existing Chat tests should be treated as behavioral regression and evaluation
cases. They do not make Agent framework migration a product goal.

## 6. Development gate

> BinderRanker is a scientific ranking and screening capability. Agent
> interfaces are optional interaction layers used to improve accessibility and
> integration, not the core product.

Before adding new Agent behavior, ask:

Does this improve BinderRanker backbone screening,
workflow reliability, evidence handling, or usability?

If the feature mainly expands a general-purpose Agent runtime, generic chatbot
behavior, memory, personality, or planning infrastructure, do not add it unless
it directly improves BinderRanker usability.

## 7. Interaction-layer engineering rule

The Agent is an optional interaction layer, not the product identity or the
scientific innovation of BinderRanker.

For generic Agent infrastructure, prefer external mature ecosystems or a
small, separately justified framework integration before building custom
runtime code.

Examples include:

- natural-language understanding;
- tool selection and tool-calling loops;
- conversation/session handling;
- model/provider portability;
- structured tool invocation;
- human-in-the-loop pause/resume;
- Agent testing infrastructure.

Custom implementation is justified when it materially improves
BinderRanker-specific scientific, workflow, evidence, safety, or
screening behavior.

The integration default is:

External Agent
→ BinderRanker Tool API
→ deterministic BinderRanker Core services
→ BinderRanker Engine.

Do not build a second general-purpose Agent framework inside BinderRanker.


## 8. Root-cause-first engineering rule

Bug fixes should target the violated architectural boundary, invariant,
or abstraction whenever practical.

Do not accumulate phrase-specific, provider-specific, or
task-state-specific patches merely to satisfy individual examples.

If fixing a behavior requires repeated special cases, keyword lists,
or additional branches in a legacy router, stop and reevaluate the
underlying abstraction first.

Tests should primarily protect behavioral invariants and Tool
contracts. Concrete user phrases are acceptance examples, not the
implementation model.


## 9. Legacy Agent runtime maintenance boundary

The handwritten Agent runtime is feature-frozen.

In particular, do not add new general Agent behavior to:

- `chat_dialogue.py`;
- `LocalAgentOrchestrator`;
- handwritten dialogue intent routing;
- legacy provider-driven Agent control flow.

Only critical compatibility, usability, data-integrity, or security fixes are
allowed. This boundary does not imply that a replacement path must be built.

New integrations should use the stable Tool API. New built-in Agent behavior
requires a direct BinderRanker usability justification.


## 10. Interaction-layer invariant

Any future interaction-layer change must preserve domain behavior without
duplicating or moving scientific authority into an Agent runtime.

KEEP:

- BinderRanker scientific logic;
- deterministic planning;
- PlanningSession semantics;
- task lifecycle and recovery;
- approval, frozen hashes, and execution guards;
- provenance and result evidence;
- scientific capability boundaries;
- deterministic validation and public error boundaries.

EXTRACT:

- preparation and resume services;
- dataset services;
- status and plan readers;
- result-analysis services;
- deterministic task navigation.

REASSESS ONLY AFTER A SEPARATE SCOPED REVIEW:

- handwritten intent classification;
- monolithic Chat routing;
- LocalAgentOrchestrator;
- provider capability-driven business routing;
- semantic fallback patches;
- legacy Agent loop infrastructure.

Existing tests protect required behavior and safety invariants, not the
continued existence of a particular runtime. They also do not require a
framework migration.

### Completed stable seams

The first provider-independent migration seams are now established:

- `PlanningSession` is a stable schema owned outside the legacy
  `LocalAgentOrchestrator`.
- `planning_session_prepare.py` owns deterministic preparation from an
  already-built `PlanningSession`; natural-language preparation is now a
  legacy/model adapter that delegates to this service.
- `planning_session_resume.py` owns deterministic continuation of
  `NEEDS_INFORMATION` sessions, including bundle validation, request-patch
  merging, re-planning, history, atomic persistence, rollback, and promotion
  to `READY_FOR_REVIEW`.
- `resume_planning.py` is now a legacy semantic adapter: it performs structured
  Provider extraction, completeness audit, and extraction reconciliation,
  then delegates state mutation to `planning_session_resume.py`.
- `dataset_advice_adoption.py` performs its own file-evidence freshness and
  user-confirmation checks, then reuses the same deterministic request-patch
  mutation core instead of maintaining a second PlanningSession state machine.
- `planning_session_builder.py` owns deterministic construction of a
  `PlanningSession` from an already-validated `UserRequest`; the legacy
  `LocalAgentOrchestrator` now delegates this business logic instead of owning
  a second implementation.
- `request_evidence.py` owns the shared provider-independent
  `UserRequestPatch` / request-evidence schema and deterministic quote
  validation. The legacy resume API keeps compatibility names but delegates
  the actual validation rules to this shared seam.
- `tool_api.py` now exposes framework-independent BinderRanker Tool API capabilities:
  task/plan reads, trusted task preparation, controlled information updates,
  task-bound dataset inspection, one-time approval creation, approved
  BinderRanker execution, and deterministic result analysis. Dataset,
  prepare-manifest, approval, and analysis paths are derived from trusted task
  state rather than supplied arbitrarily by the caller. Approval and execution
  remain two separate user-confirmed actions; the local executor retains
  ownership of the complete execution guard. `analyze_results` always uses the
  deterministic `run_analyze_run(..., with_model=False)` path and allocates a
  new non-overwriting analysis directory for each attempt.
- `analyze_run.py` keeps optional model explanation behind a lazy dependency
  seam. Importing the deterministic BinderRanker Tool API therefore does not eagerly
  load `explain_run`, `result_explainer`, Provider implementations, or the
  legacy conversational Agent runtime. Model explanation remains an optional
  enhancement outside the deterministic v0.3 Tool path.

The trust boundary is source-specific. Typed model output is not automatically
trusted. User-text supplements must pass deterministic evidence validation
before state mutation, while file-derived advice must pass its own
freshness/integrity and confirmation checks. After source validation, all
accepted updates converge on the same deterministic PlanningSession mutation
service.

The shared request-evidence seam is now used by both initial task
preparation and resume. `prepare_task` validates structured initial request
fields against trusted user text before building a `PlanningSession`, while
`provide_information` applies the same trust model to later supplements. No
full Built-in Chat or Pydantic AI runtime migration is implied by these
completed seams. Any such work remains optional and requires a separate
cost/benefit and parity review.
