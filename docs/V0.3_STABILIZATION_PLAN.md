# BinderRanker v0.3 Stabilization Plan

## Purpose

Post-release stabilization based on first-time external user testing.

Governance principle:

> BinderRanker is a scientific ranking and screening capability. Agent
> interfaces are optional interaction layers used to improve accessibility and
> integration, not the core product.

## Current Status

BinderRanker v0.3.0 has completed:

- public release workflow
- package distribution
- clean installation validation
- deterministic ranking workflow
- approval and execution safety boundaries

## User Acceptance Findings

### UX Issues

- First-time users do not know whether to run init.
- Chat entry does not clearly guide first workflow.
- Task state transitions are too exposed.
- Multiple confirmations make simple smoke tests cumbersome.
- Error messages expose internal state machine concepts.

### Agent Issues

- Conversation context recovery needs improvement.
- Planning flow is too rigid.
- Natural language requests are not always mapped to valid next actions.

## v0.3.1 User Experience Stabilization

Implemented on the stabilization branch:

- Empty Chat tasks receive a state-aware first-workflow guide.
- Default Chat startup explicitly explains that the workspace was initialized
  automatically and that a separate `binderranker init` is not required.
- First-workflow guidance offers both real-data intake and the packaged smoke
  path while preserving the small-sample claim boundary.
- API Key setup guidance is secure and platform-specific for Windows
  PowerShell and POSIX shells.
- Windows publication rewrites JSON-escaped staging paths before a Bundle is
  exposed as ready for review.
- CI runs the complete regression suite and Doctor on Windows with Python
  3.12 in addition to the existing Linux version matrix.
- Returning Chat sessions receive a read-only recovery summary built from
  deterministic Bundle evidence. It restores confirmed inputs, missing
  information, claim boundaries, pending confirmations, and the next safe
  action without relying on model memory.
- Public CLI and Chat error/status views translate internal state constants
  into deterministic plain-language progress without changing stored evidence.
- Error fallbacks recommend a stage-aware next step while continuing to hide
  exception types, internal paths, stderr, and sensitive values.
- Confirmation prompts use one compact action-and-impact format. Follow-up
  questions keep only a short reminder instead of repeating the proposal.
- Explicit “继续” expressions can confirm the currently displayed proposal;
  approval and execution remain two independent authorization boundaries.

## v0.3.1 Scientific Result Stabilization

Implemented without changing the frozen deterministic scoring core:

- A shared scientific-result validator is the common completion contract for
  local execution, result parsing, analysis, and installed-Wheel smoke tests.
- Scientific success requires complete output types, valid and unique
  candidate identifiers, at least one valid candidate, no candidate-level
  computation failures, all required finite scores, and a contiguous ranking
  consistent with descending final score.
- A process exit code of zero is recorded separately from scientific validity;
  invalid output produces a `FAILED` execution manifest and a clear reason.
- The packaged concatenated sample is normalized to target chain A and binder
  chain B before the installed-Wheel smoke run.
- Missing binder chains are rejected by the existing deterministic input
  preflight before the frozen Ranker is invoked.
- Result parsing rejects `NaN`, positive infinity, and negative infinity before
  downstream analysis can consume them.

Architecture impact:

- One validation module was added beside the execution and parsing layers.
- The frozen Ranker, score formula, Agent framework, and Tool API contracts are
  unchanged.

Validation baseline:

- Python 3.12 focused scientific-result regression: 25 passed.
- Python 3.12 full regression suite: 594 passed, 4 skipped.
- Clean sdist/Wheel build and release-asset verification: passed.
- Clean-environment Wheel installation and packaged five-candidate scientific
  smoke test outside the repository: passed.

Remaining interaction-layer follow-up, ordered within that limited scope:

1. First-run onboarding.
2. Automatic workspace initialization guidance.
3. Natural language task intake.
4. Simplified confirmation flow.

### 5. Task-state recovery summary

Goals:

- Preserve task history across sessions.
- Restore previous task state with user-friendly explanations.
- Reconstruct user-facing context from deterministic task state rather than
  expanding general-purpose conversation memory.

### 6. User-facing error translation

Goals:

- Hide unnecessary internal state machine details.
- Explain what happened, why it happened, and the next recommended action.

### 7. Guided first workflow

Goals:

Provide a complete first-run path:

install
→ initialize workspace
→ extract sample data
→ inspect PDB
→ prepare task
→ approve
→ execute
→ analyze results

## Explicit Non-goals

The stabilization phase will not:

- Replace BinderRanker deterministic core.
- Redesign scientific scoring methodology.
- Expose unpublished calibration parameters.
- Expand Agent features before runtime architecture migration.

## v0.3.2 Scientific Transparency

Priority:

1. Explain metric definitions.
2. Provide score decomposition.
3. Separate public methodology from unpublished calibration details.

Goals:

- Make ranking evidence understandable without exposing unpublished calibration choices.
- Allow users to understand why candidates rank differently.

## Post-v0.3 Development Priorities

Priority order:

1. Scientific ranking and screening capability.
2. Reproducibility and validation.
3. Stable Tool/API interfaces.
4. External Agent ecosystem compatibility.

The built-in Agent remains an optional reference interaction layer. A Pydantic
AI or other framework migration is not a planned product phase by default and
may proceed only after a separate cost/benefit and parity review. Generic
chatbot capabilities, memory/personality/planning expansion, and
general-purpose Agent infrastructure are out of scope unless they directly
improve BinderRanker usability.
