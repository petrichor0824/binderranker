# Protein Design Agent v0.3.0 Reliability Roadmap

## 1. 版本目标

v0.3.0 的目标不是扩大科研算法范围，而是修复 v0.2.0 新人测试中暴露出的可靠性、对话体验、错误恢复、模型接入和文档问题。

核心产品定位保持不变：

- BinderRanker 是确定性的科学排序与候选分层核心。
- 大模型负责理解自然语言、选择受控能力和解释已有证据。
- 大模型不能生成并直接执行任意 Shell。
- 批准、执行、分析和解释必须遵守确定性状态与安全边界。
- 不宣称预测结合亲和力、稳定性、溶解性或保证实验成功。
- 不宣称可以随意拼接、编辑或生成蛋白结构。
- 不替代 AlphaFold、分子模拟或实验验证。

## 2. 设计原则

### 2.1 模型负责语义，代码负责事实与安全

正确结构：

用户自然语言
→ 模型判断意图或选择能力
→ 确定性控制器验证阶段和权限
→ 只读或受控工具取得真实证据
→ 模型基于证据回答

禁止通过不断增加固定中文关键词来模拟自然语言理解。

### 2.2 只读能力应尽可能跨阶段可用

例如：

- 查看工作空间和当前 Bundle
- 查看任务列表
- 查看当前目录文件
- 扫描 PDB 文件
- 查看计划
- 查看状态
- 查看已有分析结果

只读动作不应因为任务处于 EMPTY 就暴露内部异常。

### 2.3 有副作用的动作继续严格控制

以下动作必须受状态机、确认和审计约束：

- 创建或修改规划参数
- 批准计划
- 执行 BinderRanker
- 创建多个数据集任务
- 调用模型生成正式结果解释
- 重置、归档或替换当前任务

### 2.4 修改策略

- 每次处理一个完整小阶段。
- 优先修复阻断用户、错误执行或错误科研结果的问题。
- 避免大范围文本替换和脆弱补丁。
- 每阶段运行语法检查、针对性测试、全量测试和 diff 检查。
- 一个完整阶段完成后再提交一次。

## 4. P0：阻断性可靠性问题

### 4.1 默认 Bundle 生命周期冲突

状态：已完成

问题：

Chat 启动时预先创建 runs/default，但自然语言 NEEDS_INFORMATION 保存逻辑再次使用 exist_ok=False，导致首次任务稳定出现 File exists。

已完成：

- 允许复用已经存在但为空的 Bundle。
- 非空 Bundle 继续禁止覆盖。
- START_TASK 进入真实 PREPARE 流程。
- 增加模块测试和 Chat 集成测试。
- 真实 Chat 已成功生成：
  - planning_session.json
  - agent_prepare_manifest.json

验收：

- 首条科研请求进入 NEEDS_INFORMATION。
- 不出现 File exists。
- 不运行 BinderRanker。
- 非空 Bundle 仍拒绝覆盖。

### 4.2 失败准备的原子回滚和任务恢复

状态：部分完成

已完成：原子准备与失败审计

- 正式 Bundle 不再作为准备过程中的工作目录。
- 所有准备产物先写入同一父目录中的 staging Bundle。
- PlanningSession、项目配置、标准化结果、工作流计划和日志只有在全部验证成功后才发布。
- workflow 返回非零状态时，不发布正式 Bundle。
- workflow 缺失关键产物或违反执行边界时，不发布正式 Bundle。
- 准备阶段意外产生 BinderRanker 正式结果时，整体回滚。
- staging Bundle 无论成功或失败都不会残留。
- 成功发布前，将可执行元数据中的 staging 路径转换为正式 Bundle 路径。
- 正式发布后的 JSON、YAML 和运行脚本不得引用 `.preparing-*` 临时目录。
- 失败日志和脱敏失败信息保存在正式 Bundle 外的 `.pda-failures` 审计目录。
- 失败审计明确记录 `formal_bundle_published: false`。
- 原有非空 Bundle 继续禁止覆盖。
- Chat 已创建的空 Bundle 仍可作为安全目标使用。

仍需完成：任务恢复

- 支持“重置当前失败或空任务”。
- 支持“归档当前任务并创建新任务”。
- 默认不得直接删除已有有效计划、批准、执行或结果证据。
- 明确区分可安全删除的空任务、失败任务和必须归档的有效任务。
- Chat 中提供受控的恢复入口和明确影响确认。
- 增加任务恢复和归档的回归测试。

验收：

- 准备失败不能留下伪装成有效任务的半成品 Bundle。
- 准备失败仍保留可审计诊断证据。
- 成功 Bundle 不得引用已经不存在的 staging 路径。
- 已有非空任务不得被静默覆盖。
- 后续恢复操作不得破坏已有有效科研证据。

### 4.3 explain-run 分析产物发现错误

问题：

analyze-run 将结果写入：

analyses/analysis_v1/

但 explain-run 仍在 Bundle 根目录查找：

agent_result_summary.json

需要：

- 不硬编码旧版根目录位置。
- 验证执行和分析指纹。
- 记录本次解释使用的分析版本和来源。

### 4.4 真实模型返回空内容

状态：待调查

问题：

外部测试中 explain-run 可能收到空 content。

禁止在没有证据时直接猜测原因。

需要记录经过脱敏的响应结构：

- HTTP 状态码
- JSON 顶层键
- choices 数量
- message 的键
- content 是否存在
- reasoning_content 是否存在
- finish_reason
- usage

禁止记录：

- API Key
- Authorization 请求头
- 完整敏感请求内容

### 4.5 通用只读能力层

状态：待处理

需要建立由模型选择、确定性代码执行的通用能力：

- GET_RUNTIME_CONTEXT
- LIST_WORKSPACE_FILES
- SCAN_PDB_FILES
- VIEW_PLAN
- VIEW_STATUS
- LIST_TASKS
- VIEW_RESULT_EVIDENCE

示例：

“现在工作目录是什么”
→ GET_RUNTIME_CONTEXT
→ 返回真实 cwd、workspace、task 和 bundle

“当前目录有 PDB 吗”
→ SCAN_PDB_FILES
→ 只读扫描，不创建任务

不得为每一种自然语言问法增加固定关键词分支。

### 4.6 错误展示分层

状态：待处理

用户界面只显示：

- 已确认的事实
- 对当前任务的影响
- 可执行的恢复步骤

审计记录保存：

- 异常类型
- 堆栈
- 内部状态
- 相关路径
- 脱敏诊断信息

禁止把模型猜测的“可能原因”直接当成系统事实展示。

### 4.7 能力边界真实性

状态：待处理

必须向对话模型明确提供真实能力说明。

禁止声称：

- 预测结合亲和力
- 预测稳定性
- 预测溶解性
- 自动保证优质 binder
- 任意拼接或编辑蛋白结构
- 替代 AlphaFold 或实验验证

## 5. P1：新人体验和产品完整性

### 5.1 Chat 启动时选择是否使用模型

状态：已完成

普通用户目标流程：

protein-design-agent chat
→ 检测配置和 API Key
→ 询问“检测到模型配置和 API Key 已就绪，是否允许本次 Chat 调用模型 API？这可能产生网络请求和 API 费用 [y/N]”
→ y：启用模型
→ n：进入离线确定性模式

要求：

- --allow-network 保留给自动化、测试和高级用户。
- 普通用户不需要记忆两个启动命令。
- 未经用户允许不得发送网络请求。
- 只询问本次会话，不静默永久授权。
- 非交互 stdin 环境不能永久等待输入。
- 明确区分：
  - 配置和凭据是否就绪
  - 用户是否允许联网
  - 是否真正完成过网络请求

### 5.2 Key、模型和 Provider 教程

状态：部分完成

已完成：

- README、QUICKSTART 和初始化终端提示均提供安全的 API Key 输入命令。
- 用户只需复制并运行一整行命令，再在终端提示出现后粘贴真实 Key。
- 明确说明输入 Key 时屏幕不会显示字符，这是正常的安全行为。
- 明确说明命令末尾的 `DEEPSEEK_API_KEY` 是环境变量名，不能替换成真实 Key。
- 避免使用会把真实 Key 直接写入 Shell 历史的示例。
- 明确说明 Key 默认只对当前终端会话有效。
- 提供不联网的模型配置验证和 `doctor` 检查方式。
- 普通用户通过 `protein-design-agent chat` 启动。
- 配置和 Key 就绪后，由 Chat 询问本次会话是否启用模型。
- 说明 `yes`、`no` 和直接回车的区别。
- 说明未配置模型时仍可使用的确定性功能。

仍需补充：

- 如何更换或撤销当前终端中的 Key。
- `export` 和环境变量作用域的更完整解释。
- 如何查看和切换模型 Profile。
- OpenAI-compatible Provider 配置示例。
- 本地模型或其他 Provider 配置示例。
- Provider 配置错误时的分层排查教程。

### 5.4 离线状态文案

状态：已完成

已完成：

- 不再笼统声称离线状态下可以创建新的自然语言规划。
- 空任务且未启用模型时，明确说明自由文本任务创建需要模型。
- 已有任务仍可使用确定性状态查看和计划查看能力。
- 已批准任务仍可在确定性安全控制器约束下执行。
- 已完成任务仍可进行不依赖模型的确定性结果分析。
- 模型配置已经就绪但用户拒绝本次联网时，状态显示为离线，而不是配置失败。
- 普通用户下次重新运行 `protein-design-agent chat` 时，可以再次选择是否启用模型。
- 兼容调用入口和普通 Chat 流程使用一致的离线能力说明。

验收：

- 未授权联网时不会初始化可调用的模型 Provider。
- 离线模式不会阻断已有任务的确定性工作流。
- 离线模式不会误导空任务用户认为自由文本规划仍然可用。
