# Protein Design Agent v0.3.0 Reliability Roadmap

## 1. 版本目标

v0.3.0 的目标不是扩大科研算法范围，而是修复 v0.2.0 新人测试中暴露出的可靠性、对话体验、错误恢复、模型接入和文档问题。

核心产品定位保持不变：

- BinderRanker 是确定性的科学排序与候选分层核心。
- 大模型负责理解自然语言、选择受控能力和解释已有证据。
- 大模型不能生成并直接执行任意 Shell。
- 批准、执行、分析和解释必须遵守确定性状态与安全边界。
- 不宣称预测结合亲和力、稳定性、溶解性或保证实验成功。
- 不宣称可以随意拼接、编辑或生成蛋白结构。
- 不替代 AlphaFold、分子模拟或实验验证。

## 2. 设计原则

### 2.1 模型负责语义，代码负责事实与安全

正确结构：

用户自然语言
→ 模型判断意图或选择能力
→ 确定性控制器验证阶段和权限
→ 只读或受控工具取得真实证据
→ 模型基于证据回答

禁止通过不断增加固定中文关键词来模拟自然语言理解。

### 2.2 只读能力应尽可能跨阶段可用

例如：

- 查看工作空间和当前 Bundle
- 查看任务列表
- 查看当前目录文件
- 扫描 PDB 文件
- 查看计划
- 查看状态
- 查看已有分析结果

只读动作不应因为任务处于 EMPTY 就暴露内部异常。

### 2.3 有副作用的动作继续严格控制

以下动作必须受状态机、确认和审计约束：

- 创建或修改规划参数
- 批准计划
- 执行 BinderRanker
- 创建多个数据集任务
- 调用模型生成正式结果解释
- 重置、归档或替换当前任务

### 2.4 修改策略

- 每次处理一个完整小阶段。
- 优先修复阻断用户、错误执行或错误科研结果的问题。
- 避免大范围文本替换和脆弱补丁。
- 每阶段运行语法检查、针对性测试、全量测试和 diff 检查。
- 一个完整阶段完成后再提交一次。

### 2.5 Architecture Slimdown

状态：架构决定已完成，迁移待执行

详细决定见：

`docs/V0.3_ARCHITECTURE.md`

核心原则：

- BinderRanker 和确定性工作流 Core 长期保留。
- Planner、生命周期、安全、批准、执行、provenance 和结果解析继续由确定性代码控制。
- 不再继续扩张旧版手写 Chat / Agent runtime。
- `chat_dialogue.py` 和 `process_chat_message()` 只维持兼容与必要的 P0 修复。
- Built-in Chat 后续逐步迁移到 Pydantic AI。
- OpenClaw 作为可选外部集成，不作为核心运行时。
- 迁移前先建立稳定、框架无关的 Tool API。
- 现有 Chat 测试作为行为回归与迁移验收基线保留。

开发门槛：

如果一个新功能主要扩展通用 Agent 能力，
而不是提高 BinderRanker 筛选、证据处理、
工作流可靠性或必要的用户可用性，
则不得继续加入 legacy Chat 实现。

状态：已完成

问题：

Chat 启动时预先创建 runs/default，但自然语言 NEEDS_INFORMATION 保存逻辑再次使用 exist_ok=False，导致首次任务稳定出现 File exists。

已完成：

- 非空 Bundle 继续禁止覆盖。
- START_TASK 进入真实 PREPARE 流程。
- 增加模块测试和 Chat 集成测试。
- 真实 Chat 已成功生成：
  - planning_session.json
  - agent_prepare_manifest.json

验收：

- 不出现 File exists。
- 不运行 BinderRanker。
- 非空 Bundle 仍拒绝覆盖。

### 4.2 失败准备的原子回滚和任务恢复

状态：已完成

#### 4.2A 原子准备与失败审计

- 正式 Bundle 不再作为准备过程中的工作目录。
- 所有准备产物先写入同一父目录中的 staging Bundle。
- PlanningSession、项目配置、标准化结果、工作流计划和日志只有在全部验证成功后才发布。
- workflow 返回非零状态、缺失关键产物或违反执行边界时，不发布正式 Bundle。
- 准备阶段意外产生 BinderRanker 正式结果时整体回滚。
- staging Bundle 无论成功或失败都不会残留。
- 成功发布前，将可执行元数据中的 staging 路径转换为正式 Bundle 路径。
- 正式发布后的 JSON、YAML 和运行脚本不得引用 `.preparing-*` 临时目录。
- 失败日志和脱敏失败信息保存在正式 Bundle 外的 `.pda-failures` 审计目录。
- 失败审计明确记录 `formal_bundle_published: false`。
- 原有非空 Bundle 继续禁止覆盖。
- Chat 已创建的空 Bundle 仍可作为安全目标使用。

#### 4.2B 任务生命周期恢复

- 新增确定性任务生命周期判定：`EMPTY`、`INCOMPLETE`、`VALID_WITH_EVIDENCE`。
- 未识别的非空内容默认按受保护证据处理，避免误删用户文件或科研证据。
- `chat/pending_action.json` 等受控 Chat 临时状态不会被误认为科研执行证据。
- 支持安全重置空任务或未完成任务。
- Bundle 外的 `.pda-failures` 失败审计不会因重置任务被删除。
- 已有有效计划、批准、执行、分析、BinderRanker 结果或未知重要内容时，禁止直接重置。
- 支持将非空任务完整归档到工作区 `archives/`，随后重新建立同名空 Bundle。
- 归档使用同一工作空间中的原子移动，不静默覆盖已有归档。
- Chat 中的 reset/archive 只生成待确认提案，不直接产生副作用。
- 用户确认前若任务状态发生变化，旧恢复确认自动失效。
- 即使 PlanningSession 等任务状态已经损坏，仍保留确定性的 reset/archive 故障恢复入口。
- 自由自然语言可以识别 reset/archive 意图，但最终是否允许执行仍由确定性生命周期 Core 决定。
- 大模型无权自行判断任务是否可以删除，也不能绕过受保护证据检查。

验收：

- 准备失败不能留下伪装成有效任务的半成品 Bundle。
- 准备失败仍保留可审计诊断证据。
- 成功 Bundle 不得引用已经不存在的 staging 路径。
- 已有非空任务不得被静默覆盖。
- 空任务和未完成任务可以安全恢复。
- 已有有效科研证据的任务不能直接删除，只能归档。
- reset/archive 必须经过明确确认。
- 等待确认期间任务状态变化后，旧确认不能继续使用。
- 当前全量测试基线：411 passed。

### 4.3 explain-run 分析产物发现错误

状态：已完成

根因：

`analyze-run` 已将确定性结果写入独立的
`analyses/<analysis>/` 目录，但 standalone
`explain-run` 仍默认读取 Bundle 根目录中的旧版结果文件。

已完成：

- 新增框架无关的确定性 `analysis_artifacts` Core。
- 显式指定的结果摘要和失败分析路径具有最高优先级。
- standalone explain 可自动发现最新有效的 `COMPLETED` analysis。
- `RUNNING` 或 `FAILED` analysis 不得作为解释证据来源。
- 从 `analyze_run_manifest.json` 解析真实结果路径，不依赖固定分析目录名。
- manifest 声明的产物必须真实存在并位于当前 Bundle 内。
- 拒绝 manifest 引用 Bundle 外文件。
- 保留旧版 Bundle 根目录结果布局的兼容读取。
- explain 结果记录本次使用的 analysis manifest 和 artifact 来源。
- `AnalyzeRunManifest` 升级至 schema `0.2`。
- 完成分析时记录：
  - `completed_at_utc`
  - `result_summary_sha256`
  - `failure_analysis_sha256`
  - `execution_manifest_path`
  - `execution_manifest_sha256`
- standalone explain 会重新验证 sealed analysis 的 SHA256。
- 结果摘要声明的 Execution Manifest 必须与分析清单 provenance 一致。
- sealed 结果在分析完成后被修改时，standalone explain 明确拒绝继续。
- 旧版未 sealed 的 analysis 可以兼容读取，但不会被错误标记为已完成 provenance 验证。
- 模型解释失败仍不得覆盖已经成功完成的确定性分析结果。

验收：

- standalone explain 不再依赖 Bundle 根目录旧路径。
- 多次 analysis 时能够确定性选择最新有效分析。
- 分析产物不能逃逸当前 Bundle。
- sealed analysis 的结果或 Execution Manifest 被篡改后必须拒绝解释。
- analyze-run 与 explain-run 的既有联合流程继续正常工作。
- 4.3 专项测试：22 passed。
- 当前全量测试基线：424 passed。

### 4.5 框架无关的只读 Tool API

状态：重新定义，待实现

Architecture Slimdown 后，本阶段不再继续为旧版
`chat_dialogue.py` 增加新的通用 Agent 路由。

需要把长期有价值的只读能力暴露成稳定、
确定性、框架无关的 Tool API，例如：

- GET_RUNTIME_CONTEXT
- LIST_WORKSPACE_FILES
- SCAN_PDB_FILES
- VIEW_PLAN
- VIEW_STATUS
- LIST_TASKS
- VIEW_RESULT_EVIDENCE

这些 Tool：

- 只能读取真实本地状态或已有证据；
- 不依赖特定模型 Provider；
- 不依赖 legacy Chat intent router；
- 不因任务处于 EMPTY 而暴露内部异常；
- 不产生科研执行副作用；
- 可以同时供 CLI、Pydantic AI 和未来 OpenClaw/MCP adapter 调用。

示例：

“现在工作目录是什么”
→ Agent 选择 GET_RUNTIME_CONTEXT
→ 确定性 Tool 返回真实 cwd、workspace、task 和 bundle

“当前目录有 PDB 吗”
→ Agent 选择 SCAN_PDB_FILES
→ Tool 只读扫描，不创建任务

自然语言理解由 Agent framework 负责，
Tool 本身只接收结构化参数并返回结构化事实。

不得为每一种自然语言问法继续增加固定关键词分支。

## 5. P1：新人体验和产品完整性

### 5.1 Chat 启动时选择是否使用模型

状态：已完成

普通用户目标流程：

protein-design-agent chat
→ 检测配置和 API Key
→ 询问“检测到模型配置和 API Key 已就绪，是否允许本次 Chat 调用模型 API？这可能产生网络请求和 API 费用 [y/N]”
→ y：启用模型
→ n：进入离线确定性模式

要求：

- --allow-network 保留给自动化、测试和高级用户。
- 普通用户不需要记忆两个启动命令。
- 未经用户允许不得发送网络请求。
- 只询问本次会话，不静默永久授权。
- 非交互 stdin 环境不能永久等待输入。
- 明确区分：
  - 配置和凭据是否就绪
  - 用户是否允许联网
  - 是否真正完成过网络请求
