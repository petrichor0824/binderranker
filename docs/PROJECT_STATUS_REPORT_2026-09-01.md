## 1. 执行摘要

BinderRanker 是一个面向生成式蛋白骨架候选的**可解释排序与分层筛选系统**。它位于候选骨架生成与昂贵的下游验证之间，用确定性的结构几何指标帮助研究者回答：一批已经生成的候选中，哪些更值得继续投入序列设计、复合体预测、分子模拟、人工检查和湿实验资源。

截至本报告日期，项目已经具备：

- 稳定且冻结的确定性 Ranker 科学核心；
- 候选排序、宽松/中等/严格三层筛选、失败原因和指标分解；
- 对科学结果语义的统一验证，不再把“程序退出成功”等同于“科学结果有效”；
- 完整 CLI、Python 接口、内置可选交互层和面向外部 Agent 的 Tool API；
- 本地只读 MCP 接口，可被 Codex 等外部客户端发现和调用；
- 可审计审批、执行状态机、结果分析与可解释报告；
- Python 3.10–3.12 与 Windows CI、Wheel/sdist 构建、哈希校验、干净环境安装和安装后烟雾验证；
- 固定预算、数据分割、基线比较、目标级敏感性分析等真实数据验证基础设施。

项目当前最准确的成熟度判断是：**工程上已经是一套较成熟、可复现、可审计的科研软件原型，可用于受控演示、方法研究和真实数据验证；但算法的真实生物学效力尚未由足够的回顾性实验数据和前瞻性湿实验建立。** 因此，当前不能把 BinderRanker 的分数解释为结合亲和力、实验成功率或生物学真实性。

## 2. 项目定位

### 2.1 BinderRanker 是什么

BinderRanker 的输入是一批针对同一目标生成的候选复合体/骨架 PDB，输出是：

1. 候选级可解释指标；
2. 批次内确定性综合分数与排名；
3. 宽松、中等、严格分层筛选结果；
4. 失败原因、相邻排名差异和分数组成；
5. 可供下游验证流程消费的结构化结果。

典型工作流如下：

```text
RFdiffusion / 其他骨架生成方法
                 │
                 ▼
          候选骨架 PDB 批次
                 │
                 ▼
 BinderRanker 确定性排序与分层筛选
                 │
                 ▼
       可解释的候选优先级清单
                 │
                 ▼
ProteinMPNN / 复合体预测 / MD / 人工检查 / 湿实验
```

### 2.2 BinderRanker 不是什么

- 它不是骨架生成模型；
- 它不是亲和力预测器；
- 它不是实验成功概率模型；
- 它不是通用聊天机器人或通用 Agent 平台；
- 它不能替代复合体预测、动力学分析或湿实验验证。

项目治理原则是：

> BinderRanker is a scientific ranking and screening capability. Agent interfaces are optional interaction layers used to improve accessibility and integration, not the core product.

即：Agent 只是改善可访问性和集成体验的可选交互层，科学能力始终位于确定性核心与稳定 Tool/API 接口中。

## 4. 系统架构

```text
        CLI / Python 用户
               │
        可选内置交互层
               │
外部 Agent / Codex / MCP 客户端
               │
               ▼
      稳定 Tool API 与授权边界
               │
               ▼
任务准备 ── 审批 ── 执行 ── 分析 ── 结果查询
               │
               ▼
      BinderRanker 确定性科学核心
               │
               ▼
 PDB 输入、CSV/JSON 结果、分析与审计资源
```

架构上严格区分四件事：

- **科学核心**：计算指标、分数、排名与筛选层；
- **执行工作流**：任务、计划、审批、运行状态和资源生成；
- **交互接口**：CLI、Python、内置交互层、Tool API、MCP；
- **科学验证**：对输出语义、数据协议和真实性证据的检查。

这种分层使外部 Agent 不能通过自然语言绕过确定性核心，也不能让“模型说执行成功”代替经过验证的运行资源。

## 5. 已完成的核心科学功能

### 5.1 确定性排序

同一输入、同一参数和同一程序版本会得到相同结果。核心根据界面几何、形态适配、安全性、表面粗糙度以及可选区域约束形成 `final_score_v4`。

无有效区域分数时：

```text
final_score_v4 =
    0.85 × morphology_adaptive_score
  + 0.10 × score_safety
  + 0.05 × score_roughness
```

存在有效区域分数时：

```text
final_score_v4 =
    0.78 × morphology_adaptive_score
  + 0.10 × score_safety
  + 0.05 × score_roughness
  + 0.07 × score_region
```

分数只用于**同一目标、同一批次候选之间的相对优先级**。项目明确禁止把它解释为跨目标可比的物理能量、结合亲和力或成功概率。

### 5.2 形态自适应评分

系统分别计算并组合线型、平面型和紧凑型等界面形态的适配得分，使单一几何假设不会垄断全部候选。最终结果保留各分量和有效权重，便于审计为什么某个候选排名更高。

### 5.3 分层筛选

宽松（broad）、中等（medium）和严格（strict）筛选层独立于连续排序分数。它们用于控制不同下游预算，而不是为高分候选贴上“成功”标签。

### 5.4 指标体系

当前结果采用受控的 20 项指标本体：

1. `final_score_v4`
2. `morphology_adaptive_score`
3. `score_line`
4. `score_plane`
5. `score_compact`
6. `score_roughness`
7. `score_microfit`
8. `score_safety`
9. `score_region`
10. `score_hotspot`
11. `effective_weight_sum`
12. `target_effective_coverage`
13. `target_contact_span_norm`
14. `backfacing_cb_far_weight_ratio`
15. `cb_closer_weight_ratio`
16. `binder_field_active_roughness`
17. `contact_map_continuity_score`
18. `contact_map_jump_fraction`
19. `shell_sensitivity_12_vs_8`
20. `clash_pairs`

文档为每项指标规定了定义、解释边界和禁止声明。分数分解功能会重新计算最终分数，并拒绝不一致的结果；相邻排名比较只陈述确定性数值差异，不将相关性包装成因果解释。

## 6. 科学可信度与结果验证

### 6.1 统一科学结果验证层

系统已经把“进程执行成功”和“科学输出有效”拆成两个状态。一个命令即使退出码为 0、文件也存在，只要输出没有有效候选、缺少必要排名字段、候选标识非法、分数出现 `NaN`/`+Inf`/`-Inf` 或排名结构畸形，就不能被标记为科学成功。

验证层被统一接入：

- 本地执行完成门；
- 结果解析器；
- 分析入口；
- Wheel 安装后烟雾测试；
- Release 资源验证流程。

这解决了早期“文件存在即可 PASS”的根本问题。

### 6.2 输入与执行安全边界

系统支持：

- binder chain 缺失时快速失败并给出明确原因；
- 输入 PDB 和任务资源检查；
- 计划、审批与执行状态机；
- 审批资源绑定，防止审批后更换执行内容；
- 可信运行时签发的短时、单次、不可由模型伪造的执行能力；
- 统一且不泄露主机路径/凭证的适配器错误语义。

### 6.3 可复现发布验证

发布验证覆盖：

- 完整 pytest；
- Wheel 和 sdist 构建；
- SHA256 清单和发布资源校验；
- 干净环境 Wheel 安装；
- 使用随包 5-PDB 示例执行安装后科学烟雾验证；
- 安装后 MCP 子进程与协议烟雾验证。

## 8. 外部 Agent、Tool API 与 MCP

### 8.1 Tool API 契约

当前 Tool API 契约版本为 `0.3`，包含 10 个操作：

| 操作 | 副作用等级 | MCP 暴露 |
| --- | --- | --- |
| `get_current_plan` | 只读 | 是 |
| `get_task_status` | 只读 | 是 |
| `provide_information` | 修改但不执行 | 否 |
| `prepare_task` | 修改但不执行 | 否 |
| `inspect_dataset` | 只读 | 是 |
| `request_approval` | 改变授权状态 | 否 |

该设计有意先开放低风险发现和查询能力，再逐步设计外部 Agent 的写入、审批与执行流程。MCP 返回投影不包含本地主机路径、自由文本任务名或凭证。

### 8.2 本地 MCP 能力

项目已经完成基于官方 MCP SDK 2.x 的本地 stdio 适配器，并用真实 Codex 隔离工作区进行了协议调用验证。当前五个只读工具可以：

- 查看当前计划；
- 查看任务状态；
- 检查数据集摘要；
- 读取最新密封结果摘要；
- 分页发现可访问任务。

任务发现能够跳过无效目录/符号链接，隔离损坏任务，避免单个异常资源破坏整个枚举结果。

### 8.3 当前尚未开放的集成能力

- MCP 写入、审批、执行和分析工具；
- 面向互联网的远程 MCP 服务；
- 多租户隔离、调用者身份与组织级权限；
- 托管式生产 API/SLA；
- Secure MCP Tunnel 的真实外部凭证端到端验收。

仓库已经包含安全隧道的准备度与威胁模型，但在缺少明确外部账号、凭证和权限时不会假装完成远程上线。

## 9. 真实数据科学验证基础设施

在不改变冻结评分算法的前提下，项目已经建立 v0.5 工作流所需的验证协议：

- SHA256 密封的基准数据包；
- 结果标签、基线和 Ranker 版本的来源记录；
- 固定计算/实验预算；
- calibration 与 evaluation 分割；
- 候选标识、有限分数、唯一排名和目标泄漏检查；
- 仅在 evaluation 集上执行固定预算基线比较；
- campaign 级和 pooled 指标；
- 没有阳性样本时明确将 recall/enrichment 标记为不可用；
- 等目标权重摘要和 leave-one-target-out 敏感性分析。

这些功能意味着项目已经准备好接收规范化的真实回顾性数据，但**基础设施完成不等于算法效果已被证实**。目前仓库中的合成夹具用于验证协议和程序正确性，不能替代真实 campaign 或湿实验结果。

## 12. 当前能够与不能够做出的声明

### 可以声明

- BinderRanker 能确定性地对同批候选骨架进行可解释排序和分层筛选；
- 软件具备统一的科学结果验证和完整的可复现执行链；
- 软件能够拒绝零有效候选、缺失字段、非有限分数和畸形排名；
- 软件具备跨平台 CI、发布包验证和安装后科学烟雾测试；
- 项目已经准备好开展真实回顾性数据的固定预算比较；
- 外部 Agent 可以通过本地 MCP 安全读取经过投影的任务与结果信息。

### 不能声明

- 高分候选一定具有更高结合亲和力或实验成功率；
- `final_score_v4` 可跨目标直接比较；
- 当前合成测试已经证明真实生物学性能；
- BinderRanker 可以替代下游复合体预测、模拟或湿实验；
- 项目已经具备公网、多租户生产服务的安全与运维成熟度。

## 13. 主要剩余风险

1. **真实证据不足**：最大的风险不在代码，而在缺少可审计的真实 retrospective campaign 和前瞻性湿实验数据。
2. **数据分布风险**：不同目标、生成器和结构类型可能导致当前批次相对排序规律迁移。
3. **标签质量风险**：失败样本、选择偏差和不完整实验记录会影响基线比较。
4. **外部执行风险**：开放 Agent 写入/审批/执行能力前，需要更严格的调用者身份、重放防护和最小权限设计。
5. **版本认知风险**：v0.5/v0.6 是开发工作流，不应在正式 Release 审阅前被误称为已发布版本。

## 14. 推荐后续路线

### 阶段 A：安全的外部 Agent 任务接入

在保持执行工具关闭的情况下，先定义结构化任务提交、数据准备和人工确认边界；为每个写操作增加幂等性、审计资源和稳定错误语义。

### 阶段 B：真实回顾性验证

收集带有明确 target、候选、实验结果和选择过程的真实 campaign 数据，按现有协议密封；预先确定预算、基线和分割后运行 evaluation，报告目标级差异和失败案例。

### 阶段 C：前瞻性湿实验闭环

在预算允许时，让 BinderRanker 与合理基线在相同候选池和相同预算下提出候选，进行盲法/预注册式验证。结果无论正负都回写为可审计证据，而不是直接修改冻结算法追逐单次实验。

### 阶段 D：远程 API/MCP 产品化

只有在明确使用场景需要时，再引入远程身份、租户隔离、队列、资源限额、审计日志、凭证托管和运维监控。Agent 兼容性继续围绕稳定 Tool/API 契约建设，不扩张为通用聊天基础设施。

### 阶段 E：正式版本发布

对 `Unreleased` 开发链进行独立发布审阅，明确哪些内容属于 v0.5 科学验证基础设施、哪些属于 v0.6 外部集成；通过后再更新版本、生成资产、签署 SHA256 并创建正式 Tag/Release。当前报告本身不创建新版本标签。

## 15. 面向老师的汇报提纲

可用以下五句话概括项目：

1. BinderRanker 解决的是生成后、昂贵验证前的候选优先级问题，不负责生成蛋白，也不是通用 Agent。
2. 它使用冻结、确定性的界面几何和形态指标，对同批候选进行可解释排名和三层筛选。
3. 项目已经完成从 PDB 输入、任务准备、审批、执行、科学语义验证、分析、打包到跨平台 CI 的完整工程闭环。
4. 目前还建立了面向真实数据的固定预算验证协议，以及供 Codex 等外部 Agent 使用的只读 Tool API/MCP 接口。
5. 当前最大未完成项是真实 retrospective 与湿实验效力验证，因此可以说“软件与验证基础设施成熟”，不能说“生物学性能已被证明”。
